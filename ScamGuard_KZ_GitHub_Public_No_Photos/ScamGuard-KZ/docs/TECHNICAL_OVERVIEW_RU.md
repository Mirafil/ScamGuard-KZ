# Техническое описание ScamGuard KZ — конкурсная версия

**Команда:** Абдрашитова Альмира, Макулбаева Адель, JUR-2403IJ; студентки 3 курса факультета журналистики.

## 1. Что разработано

ScamGuard KZ — учебный MVP оценки риска переводов **до их выполнения**. Веб-интерфейс содержит модель банковского приложения, конструктор транзакций, карту вымышленных предыдущих связей получателя и Validation Lab. Локальный Python-сервер предоставляет тестовый эндпоинт `/v1/transaction/check` с API-ключом и SQLite-аудитом.

**Ограничение:** это не подключённая к банку система, не самостоятельная обученная ML-модель, не доказанный в банковских условиях антифрод и не инструмент для персональных банковских данных.

## 2. Методика

Модель: `rules-mvp-1.0` (детерминированная rule-based оценка). Сумма баллов активированных правил ограничивается 100:

| Признак | Вес |
|---|---:|
| Ранее неизвестный получатель | 14 |
| Сумма >= 2 × привычная сумма | 16 |
| Сумма >= 5 × привычная сумма | 9 |
| Новый счёт получателя | 10 |
| Нетипичное время | 9 |
| >= 10 разных отправителей в прежней истории | 18 |
| Быстрый вывод прошлых поступлений | 16 |
| Связь с исторически отмеченными рискованными счетами | 17 |

В демонстрационной политике риска: 0–39 → ALLOW; 40–74 → VERIFY; 75–100 → HOLD. Это рекомендации для банка, не автоматическая блокировка. Балл 0–100 не является калиброванной вероятностью мошенничества.

Правила есть в `server.py` (`RULES`), а их версия для браузера — в `index.html` (`RISK_RULES`).

## 3. Датасет

`data/synthetic_validation_600.csv`: **600 искусственных операций** с колонками `amount`, `usual_amount`, `known`, `new_account`, `odd_time`, `multi_senders`, `rapid_outflow`, `risky_links`, `is_fraud`. Генератор данных содержится в `tools/reproduce_validation.py` и повторяет seed `20261008` и структуру генератора браузерной лаборатории.

Метки `is_fraud` создаются стохастически на основе синтетических предположений, использующих пересекающиеся признаки. Это не независимая внешняя разметка и не реальные банковские операции.

Входные признаки должны быть известны **на момент до текущего перевода**. Нельзя использовать будущие движения средств. Для реальных данных потребуется контролировать временную утечку, независимость выборки и юридические основания.

## 4. Воспроизводимые результаты: искусственная лаборатория

Тестовый порог: Risk Score >= 40 отмечаем как сигнал риска (включает VERIFY и HOLD), ниже порога — отсутствие тревоги. Результаты фиксированы в `results/synthetic_metrics_threshold40.json`.

- TP = 88 (мошенничество обнаружено)
- FN = 40 (мошенничество пропущено)
- FP = 171 (ложное предупреждение)
- TN = 301 (правильно пропущенная обычная операция)
- Recall = 68.75%
- FPR = 36.23%
- Precision = 33.98%
- F1 ≈ 45.48%
- Accuracy ≈ 64.83%

**Вывод:** текущие правила дают много ложных срабатываний и пропускают мошенничество. Такие результаты **недостаточны для внедрения в банк**. Преимущество перед банковскими системами пока не доказано. Учебный baseline в отчёте не представляет реальный банковский антифрод.

Числа воспроизводимы командами:

```
python tools/reproduce_validation.py
python -m unittest discover -s tests -v
```

Измерение времени `performance.now()` в браузере относится к локальному вычислению правил, **не к задержке банковского API**. Промышленная latency пока не доказана.

## 5. Проверяемый тест-кейс

Вход: `example_transaction.json`, сумма 150000 KZT, привычная сумма 25000 KZT, новый получатель и счёт, 29 предыдущих отправителей, быстрый вывод в прошлом, рискованные исторические связи. Временная отметка истории раньше момента запроса. Ожидаемый результат: Score 100, рекомендация HOLD. Автоматический тест находится в `tests/test_app.py`.

## 6. Технологическая готовность / TRL

**Предварительная самооценка:** TRL 3–4 для демонстрационного rule-based MVP с лабораторными проверками. Это не сертифицированный уровень, промышленной банковской среды пока нет. Для будущей ML-модели готовность ниже: обучение и независимая валидация не выполнены.

**План (зависит от доступа к данным и партнёрам):**
1. Месяц 1: документация, повторяемые тесты, аудит утечек и качества синтетической схемы.
2. Месяц 2: законное получение и обезличивание независимых размеченных исторических данных.
3. Месяц 3: обучение/настройка модели, сравнение с baseline, контроль ложных срабатываний.
4. Месяц 4: защищённая архитектура API, разграничение доступа, журналирование, резервные сценарии.
5. Месяц 5: проверка нагрузки и качества в среде, приближённой к банковской (целевой TRL 5).
6. Месяц 6: при наличии соглашения с банком — ограниченный пилот, аудит и метрики реальных операций.

## 7. Исходники и запуск

- `index.html`: frontend (можно открыть автономно без сервера).
- `server.py`: **только локальный** HTTP API на `127.0.0.1:8765`, стандартная библиотека Python.
- `tests/`: автоматические тесты.
- `tools/reproduce_validation.py`: воспроизведение искусственного набора и отчёта.
- `README.md`: полная инструкция.
